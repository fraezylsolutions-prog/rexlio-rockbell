# Rexlio POS — Modification Implementation Roadmap

This document lists all feature modifications identified during the Phase 2 audit, in build sequence. Status reflects progress as of the latest working session.

## Phase A: Quick Wins (no dependencies) — DONE
1. POS table selection popup — show table name only, remove image. Implemented via scoped CSS override under #show_tables_modal2 (could not edit the DB-stored floor-plan markup directly). Later reverted per decision to keep original table images.
2. *(Deprioritized/backlog)* Order print-out (KOT) price display — left as-is per decision; invoice already shows price correctly.

## Phase B: Filters & Reporting on Existing Data — DONE
3. List Item (Ingredient) screen filters — DONE. Added: name/code search, category, purchase unit, consumption unit, and Type (is_direct_food: separates true ingredients from auto-generated product-type stock rows created by direct-sale food menu items). Verified against scratch DB and live-tested with seeded data.
4. List Purchase & Purchase Report filters — DONE. Shared filter set (date range, supplier, payment status, category, item) implemented once in Purchase_model::getFilteredPurchases() and used by both screens. Key decisions: single-date filter = exact day only; no dates submitted = returns all matching results (enables supplier/category/item-only searches). Payment status is derived from tbl_purchase.due (not a true "settled" status — supplier payments recorded later aren't reflected). Verified against scratch DB and live-tested with seeded data including a due=NULL edge case.
5. Stock Report — DONE. New screen at Report/stockReport (sidebar: Report → Stock Report). Built from Inventory_model::getStockLedger() — one grouped query per ledger source (8 sources), merged in PHP; opening + in − out = closing by construction. Key decisions: consumption counts completed orders only (order_status=3) for main audit totals; cancelled/voided orders cannot be shown (system hard-deletes their consumption records) — a separate "Non-audit stock impact" section instead shows open/uncompleted orders and refunds; fixed the legacy broken unit display ("3.2 = 3 bottles + 2 litres" string-hack) to show clean real numbers; added ~25 database indexes (previously zero indexes existed on any ledger date/foreign-key column) with tested rollback script; outlet-scoped with a selector, defaulting to current outlet. Fully verified against a fixture designed to break naive implementations (fractional conversion rates, cross-outlet isolation, zero-activity items, etc.) and live-tested.

*Note: stock is a computed ledger (purchases, consumption, waste, adjustments, transfers) — these were reporting/query-layer additions requiring no core schema changes (aside from the new indexes).*

## Phase C: New Screens — DONE
6. Dedicated Running Order screen — DONE. Entry point: new toolbar icon in the POS top bar, not sidebar. Card-grid layout showing customer name, waiter name, order number, table number, and action buttons (Modify Order, Order Details, Re-print KOT, Invoice, Bill, Cancel Order). Filter/search for all users (table, order number); extra waiter/user selector filter reserved for Admin + roles named "Leader"/"Sales Supervisor" in tbl_roles (case-insensitive) — these roles do not yet exist on this install, so currently only Admin sees the selector.

   **Major architectural finding:** running/uninvoiced orders do not exist in tbl_sales at all — they live only in browser IndexedDB until invoiced. The correct live data source is tbl_kitchen_sales, populated immediately at order placement (via Sale/add_kitchen_sale_by_ajax, fires for every order type unconditionally) and auto-cleared on completion/cancellation. Monitor::runningOrders() / orderDetailsAjax() built against getRunningKitchenOrders().

   Of the 6 action buttons, only Order Details works fully server-side (new Monitor::orderDetailsAjax() endpoint with ownership/escalation checks). The other 5 (Modify, Cancel, Invoice, Re-print KOT, Bill) are IndexedDB-authoritative and deep-link back into the POS via a new `?open_sale_no=` URL parameter, with client-side polling (IndexedDB cursor-completion signal, ~150-300ms) to auto-select the order once the POS loads. Real, accepted limitation: deep-link only works if the order exists in the current device/browser's IndexedDB under the same logged-in user who placed it — cross-device/cross-staff monitoring cannot open another user's order this way (no server-side fix possible without touching IndexedDB architecture, deliberately left alone).

   Offline behavior: these are supervisor/monitoring screens requiring server connectivity to load (no offline shell for page navigation exists in this product) — the POS itself remains the true offline-capable surface for order-taking. Documented as an accepted architectural boundary, not a bug.

7. Dedicated Table screen — DONE. Reuses Running Order screen's polling/offline-banner/timer/deep-link infrastructure. New toolbar chair icon, route table-status. Core occupancy logic verified against real live data (5 tables, 3 correctly occupied with right guest counts/waiters/orders, including simultaneous multi-table occupancy). "Table frees on order completion" path fully verified against a real completed order after the sync bug fix below.

   **Base-product bug found and fixed during this work (not introduced by Rexlio changes):** completed orders were never syncing to tbl_sales at all — a pre-existing defect in iRestora PLUS affecting the entire product's sales reporting, not just this screen. Root cause: in push_online() and push_online_sync() (pos_script), `JSON.parse(cursor.value.order)` ran unconditionally on every row in the recent_sales IndexedDB store *before* checking `online_push === 0`. If any single row's stored order JSON was malformed, the parse threw inside the IndexedDB cursor's synchronous onsuccess callback, silently killing the entire cursor pass — no error surfaced, no server request made, and the failure repeated identically every 10-second interval indefinitely. Fixed by moving the online_push check before the parse and wrapping the parse in try/catch so one bad row can no longer block the whole queue. Verified live: zero Sale/push_online calls in the install's entire history before the fix; four successful syncs immediately after (draining the backlog), and further orders (aND260814-001) confirmed syncing end-to-end within ~51 seconds of completion on a fresh test. This fix means the product's sales reports will now reflect real data going forward — a significant fix beyond just unblocking the Table screen.

   Two related, smaller issues found and left documented rather than fixed (out of scope for this task): (1) update_online_push() matches on a local IndexedDB auto-increment key against the server's returned sale id — these id spaces don't correspond, so once syncing works, rows may not always get correctly flagged as sent; observed behavior post-fix showed no duplicate tbl_sales rows, so this has not caused visible harm, but the mismatch is real and worth revisiting if duplicate syncs are ever seen. (2) The root cause of *why* the original stuck rows' JSON was malformed in the first place was never identified — the backlog drained cleanly before the diagnostic console.warn could capture it.

## Phase D: Pricing Tier Expansion — DONE (VIP and Club as two distinct tiers; built, tested, confirmed)
8. Add VIP/Club price tiers — DONE. Initially shipped as a single combined "VIP|Club" button (a deliberate scope simplification, see "Scope decision" below), then **split into two independent VIP and Club tiers** once the client committed to them as genuinely distinct — see "Completed after first release" below for the split and the corrected diagnosis that prompted it.
9. Counter-level default price tier assignment — DONE. Dropdown on counter add/edit writing `tbl_counters.default_price_tier`, which also drives the counter tier **lock** (non-Regular tier = whole order-type row fixed for ordinary staff; Admin/Manager override).
10. Rename "Dine In" → "Regular", "Take Away" → "Outlet" — DONE (English only; see Still open).

   **Scope decision:** the original plan (admin can create/edit/delete arbitrary price tiers dynamically) was evaluated and intentionally scaled back to a fixed-column approach — same pattern as the existing dine-in/take-away/delivery prices — to keep the touch surface and risk lower. A fully dynamic tier system remains a documented future option if a client ever needs more than the fixed set.

   **Architecture:** a new `price_tier` field was added, kept deliberately *separate* from the existing `order_type` field, after investigation confirmed `order_type` was doing double duty — driving both fulfillment classification (dine-in/take-away/delivery) AND price selection AND table-availability gating, all from the same value. Adding VIP/Club as new order_type values would have required auditing 17 distinct table-gating sites plus every order_type consumer (invoices, KOT, reports, kitchen panel) with real risk of silently mistreating a VIP/Club order as an unrecognized fulfillment type. The separate-field design means VIP/Club orders never touch order_type at all (they record as order_type=1/Regular under the hood, so all existing reporting/table-gating logic requires zero changes), while `price_tier` independently drives which price column is read via a single resolver function.

   **What shipped at first release** *(historical — see "Completed after first release" below for the VIP/Club split and the counter tier lock, which superseded parts of this):*
   - Schema: `sale_price_vip`, `sale_price_club` columns on tbl_food_menus (fallback rule: NULL/empty falls back to Regular price, matching the existing pattern); `price_tier` tinyint on tbl_kitchen_sales, tbl_sales, and tbl_holds (added to tbl_holds after catching a near-miss where a held order would have thrown "Unknown column" without it); `tbl_price_tiers` reference table (id, tier_key, tier_name, price_column, is_active, sort_order, company_id, del_status), seeded with all 5 tiers for every Live company. Note `price_column` stores the tbl_food_menus column name each tier reads (`sale_price`, `sale_price_take_away`, …) so the mapping lives in data rather than being hardcoded at each price-selection site; `tier_key` (1–5) is the stable identifier written to orders, deliberately separate from the auto-increment `id`. `default_price_tier` on tbl_counters.
   - Sale screen: a single new **VIP|Club** button added alongside Regular/Outlet/Delivery/Table in the main order-type row (not a separate row — an earlier iteration added a full 5-pill secondary "Price Tier" row below the main row; this was built, tested, then reverted in favor of the simpler single-button approach after review). Clicking VIP|Club sets `price_tier` only, explicitly does NOT change `order_type` (fixed at three sites — 8377, 8903, 10489 in pos_script — where order_type is derived from the clicked button; VIP|Club is treated identically to the Regular/dine-in branch there, including the same waiter/customer validation, so it correctly records as order_type=1 rather than writing an invalid 0). `#selected_price_tier` is the single source of truth, set by all four buttons on click, so returning to Regular after selecting VIP|Club correctly resets pricing.
   - **Label reasoning at first release (since superseded):** "VIP|Club" was deliberately shown as combined literal text, not a placeholder oversight. Different future clients on this Rexlio base will want different terminology for the same underlying tier (some call it "VIP", others "Club") — this build is a temporary substitute pending a larger modular product (Nuvora) where per-client configurable labels will exist properly. It was bound to tier_key 4 (sale_price_vip) as the first slot, with sale_price_club/tier_key 5 present in schema but unused. **This is no longer current** — the button was later split into independent VIP and Club buttons and both price columns are now in use; per-client label configuration remains a Nuvora concern.
   - Food Menu add/edit form: added "Sale Price (VIP/Club)" field, bound to sale_price_vip.
   - Table selection preserved for VIP|Club (confirmed: only Delivery disables the table button, across all three gating sites; VIP|Club never sets order_type=3, so nothing disables it).
   - Renames confirmed safe via exhaustive search — "Dine In" and "Take Away" are display-only strings; zero logic anywhere compares against either literal. Renamed to "Regular" and "Outlet" respectively across the English lang file, POS script literals, and relevant PHP sites (Sale.php, getOrderType() helper). **Not yet done:** French, Spanish, and Arabic language files still contain the old "Dîner dans"/"À emporter" equivalents — deliberately left untranslated since "Regular"/"Outlet" are client terminology choices, not something to auto-translate; flagged for a human decision later.

   **Regression found and fixed:** adding the VIP|Club button made the order-type button row 5 items wide against a CSS Grid hardcoded to `repeat(4, 1fr)` (style2.css:231) — a leftover from when the row held exactly 4 buttons. This forced the 5th button (Table) onto a wrapped second row, adding ~43px of height that pushed the footer action row (Cancel/Draft/Quick Invoice/Place Order) below the visible viewport, appearing as if those buttons had vanished. Not a width/responsive issue — reproduced identically at 1280px, 1440px, and 1920px viewports via a real browser-based test harness. Fixed by changing the grid to `repeat(5, 1fr)` with gap trimmed 10px→8px. Verified at all three widths post-fix: single row, no text clipping, footer visible again.

   **Known fragility, documented for future work:** a function `setHeightInComponent()` exists in the codebase specifically to recalculate `.main_center` height accounting for `.main_top`'s actual height — but it is dead code, defined and never called anywhere. This means the layout has no self-correcting mechanism; if a 6th button is ever added to this row (e.g., when VIP and Club are split into two independent buttons per the deferred item below), the exact same footer-disappearing bug will reproduce. The durable fix (wiring up setHeightInComponent() on load/resize) was deliberately not done as part of this fix — it's a change to global page sizing that needs a live POS login to verify safely, and wasn't required to resolve the immediate regression.

   Full reasoning, schema, completed/dropped/open items, and the three-site order_type trap are documented in `PHASE_D_PRICING_TIERS.md` in the project root. Its **section 9** ("Known fragility: the sale-screen button row holds exactly 6 buttons") now records the full history — 4 buttons originally, 5 with VIP|Club (which broke the footer), 6 after the split (fixed pre-emptively in the same change) — and gives the procedure required before adding a **7th**: raise the grid to `repeat(7, 1fr)`, bump the `style2.css?v=` string, re-verify one row at ~45px with no truncated labels, and update the three order_type derivation sites. It also notes that 7 equal columns will be tight enough that wiring `setHeightInComponent()` is probably the better answer at that point.

### Phase D — Completed after first release
- **VIP/Club split — DONE.** The single combined VIP|Club button was replaced by two independent buttons: `vip_button` (tier_key 4, sale_price_vip) and `club_button` (tier_key 5, sale_price_club), each carrying its own `data-tier_key`. The Food Menu add/edit form now has separate **"Sale Price (VIP)"** and **"Sale Price (Club)"** fields, both persisted by FoodMenu.php. All three `order_type` derivation sites were updated to recognise both new button ids (a button they don't recognise leaves order_type=0).

  **Corrected diagnosis worth recording:** this split was triggered by a report that "a counter set to Club does not lock, while VIP does". Investigation proved **the counter lock was never broken for Club** — `getLockedPriceTier()` decides with `($tier > 1)`, a range test that always included tier 5, verified by replaying it against live data for every counter. The reported behaviour was the combined effect of two real defects that together are indistinguishable from a broken lock: (1) the single button was hardcoded `data-tier_key="4"` (mirrored in two more places in pos_script), so tier 5 was unreachable by manual selection and only ever applied via a counter lock; (2) `sale_price_club` was NULL on every item, so the resolver's fallback returned the Regular price for Club on every line. Lesson: check the price columns and the button's tier key before suspecting the gate.
- **Counter default price tier dropdown — DONE.** Added to counter add/edit, populated from tbl_price_tiers, defaulting to Regular. It also became the control for the counter tier **lock** (see Register/counter-lock notes).

## Phase E: Naming Clarification & Rename — DONE
11. Rename "Ingredient" → "Item" throughout the UI — DONE. Business reason: staff found "Ingredient" confusing because the list actually shows sellable products. The underlying cause (confirmed in Phase B) is that tbl_ingredients is a mixed table — hand-entered raw ingredients (is_direct_food=1) alongside auto-generated stock rows for direct-sale food menu items (is_direct_food=2).

   **Option A vs B — why the blanket rename won.** Two approaches were costed. *Option A (split-aware labelling)* would show is_direct_food=2 rows as "Item" and is_direct_food=1 rows as "Ingredient" per row. *Option B (blanket rename)* renames everything to "Item". The enumeration settled it: the word appears in **32 language keys across 46 view files**, but only **4–5 of those locations have `is_direct_food` available per row** (the item list, inventory, inventory alert list, inventory report — all of which already branch on it for unit display). Everywhere else it is a static label with no per-row context at all: sidebar entries, screen titles, "Add Item" forms (is_direct_food isn't known until save, and =2 rows are auto-generated, never created there), "Item Category"/"Item Units" master-data screens, column headers, tooltips. So **Option A would not have replaced Option B's work, it would have added to it** — you would still have to choose a single word for ~41 locations — and the result would have been an inconsistent vocabulary: a row labelled "Item" in a list, reached from a menu called "Ingredients", edited on a form headed "Edit Ingredient". Decisive additional point: the precision Option A was reaching for **already exists** where it is actionable — the Phase B Type filter labels rows Ingredient vs Product and lets staff filter to either. That filter's wording was deliberately left untouched ("Item screen, filterable by Ingredient or Product" reads correctly).

   **The `ing_type = 'Plain Ingredient'` landmine.** `tbl_ingredients.ing_type` stores the literal string `'Plain Ingredient'` as DATA, not as a label, and it is used in WHERE clauses. A full-tree scan found exactly **7 usage sites**: `Ingredient.php:87` and `Purchase_model.php:40` (both *data filters* — break them and the item list and the purchase item picker silently return nothing), plus five per-row display branches in `inventory.php` (×2), `inventoryAlertList.php` (×2) and `inventoryReport.php`. A naive find-and-replace of "Ingredient" across the codebase would have broken all seven. The rename was therefore **confined strictly to `lang()` values** — no view, controller or model was edited, which is verifiable from file timestamps. Because `'Plain Ingredient'` never appears inside a lang value, the two layers cannot collide. Verified after the change: all 7 sites byte-identical; item list returns 7 rows; purchase picker returns 7 options; inventory unit display still splits correctly for fractional conversion rates (Whiskey 0.7, Coke 24, Water 12) and shows single units for conv=1.

   **Scope:** 31 language values renamed in `english_lang.php` — core item screens plus the embedded labels across purchases, waste, transfers, adjustments, recipes and reports. No keys added or removed. Also confirmed no logic anywhere compares against the literal UI string "Ingredient" (same diligence as the Dine In / Take Away checks).

   **Deliberately preserved exception:** `$lang['food_type_tooltip']` still reads "The item that you produce in kitchen using **ingredients**". Here "ingredients" means *recipe components*, a genuinely different concept from the screen label — renaming produces the nonsense "the item you produce in kitchen using items". Flagged rather than force-renamed.

   **Minor pre-existing issue noted (unrelated to this work):** `$lang['ingredient_category']` is defined **twice**, at line 444 and line 605. PHP takes the last definition, so line 444 is dead code. Both were renamed so behaviour is unchanged, but the duplicate is worth cleaning up separately.

   **Not done:** French, Spanish and Arabic files keep the old "Ingredient" wording — same caveat as the Regular/Outlet rename. "Item" is a client terminology choice rather than a literal translation, so each language needs a human decision.

## Phase F: Store & Stock Structural Foundation — DONE (F0–F5; F6 deferred)
*(Largest phase — Phase G depends on this being complete. Staged like Phase D: each stage independently testable and revertible.)*

**Design decisions taken at the start of the phase, all client-confirmed:**
- **Central Store is a dedicated Outlet, not a new "Store" concept.** Item 12's original framing (build store locations using the counter-creation UI pattern) was dropped: outlets already carry everything a store needs — purchases bind to them, transfers move between them, the ledger is scoped by them. A new parallel concept would have duplicated all of it.
- **Central purchasing is OPTIONAL, not forced (Option B).** Outlets keep the ability to purchase directly; Central Store is an additional pattern for bulk and distribution. Forcing all purchase through Central Store (Option A) was costed and rejected: every ad-hoc purchase would need two documents (a Central Store purchase plus a transfer) or go unrecorded, and it would make the transfer *receipt* step load-bearing daily when that step currently has no reminder, no notification and no incoming-transfer view. Option A remains available later as a per-outlet "purchasing disabled" flag.
- **Item 15's rule was CORRECTED.** The original roadmap wording said "block if **either** main store **or** counter/location stock is zero". This is now: **block only when the SELLING outlet's own stock is zero.** Central Store being empty must not stop a bar selling stock it already holds locally.
- **Sequencing constraint that cannot be reshuffled: F3 → F4 → F5.** The oversale policy (item 17) must exist before the zero-stock block (item 15), because the block reads the policy. Building the block first would mean writing the check twice, and the interim state would be a hard block with no way to switch it off.

### F0 — Verification harness — DONE
Scratch database `rexlio_f0` (full copy of production) plus a fixture whose every figure is hand-computable, built on a fresh item and food menu so no pre-existing row could contaminate the totals. Verified: per-outlet closing balances, the **All Outlets** combined figure (transfers net to zero across a complete set: 250 purchased − 100 out + 100 in − 10 sold = **240**), stock in transit invisible to everyone, and committed stock across **all three product-type branches** of the consumption writer. This harness is the basis for F2's and F3's testing. **The `rexlio_f0` database itself was dropped once Phase F completed** — the harness is described here for the record and is cheap to rebuild from a fresh clone if a future stage needs it.

### F1 — Central Store + outlet access control — DONE
**Pre-cleanup:** 16 stranded kitchen-sale headers (19 detail rows) from Phase C / waiter-PIN testing were cleared first — they would have permanently inflated F3's committed-stock figure. Confirmed test data before deleting: every one attributed to waiter_id 45/46 (the "Test Waiter Jacky"/"Test Waiter Rony" fixture accounts), all outlet 1, all dated 2026-08-13…15, none with a `tbl_sales` row. Cleared via the product's own cancellation path (`Sale::add_cancel_audit_report()`, Sale.php:1834-1906) — the same three hard deletes in the same order, preceded by one `tbl_audit_logs` row per order. Two deliberate deviations: the 16 `tbl_notifications` inserts were skipped (transient alerts for a shift that wasn't running; the durable audit trail is the part that matters), and `tbl_orders_table` was left alone because the product's cancel path never cleans it either — safe because `Sale_model::getTableStatus()` joins **from** `tbl_kitchen_sales`, so orphan booking rows cannot render as occupied.

**Schema:** `tbl_outlets.is_sales_enabled TINYINT NOT NULL DEFAULT 1`. Default 1 makes the migration a behavioural no-op — same principle as `price_tier DEFAULT 1` in Phase D. Central Store created as **outlet id 4** with `is_sales_enabled = 0` and an empty `food_menus` list (defence in depth: `getFMIds()` feeds that CSV into a `FIND_IN_SET`, so an empty list renders zero sellable items even if the guard were bypassed).

**Security fix — `setOutletSession()` trusted the URL.** `Outlet::setOutletSession()` set the outlet session after checking only that the user held `enter-67`, never that the outlet was one of theirs. Combined with `Custom::encrypt_decrypt()` being a **no-op passthrough**, the "encrypted" id in the URL is the raw id, so any user who could reach that route could enter **any** outlet in the company by editing the URL. The outlet *list* was filtered (`Common_model::getAllOutlestByAssign()`) but the entry point was not, making the filtering cosmetic. Fixed with `canEnterOutlet()` (my_helper.php), which reads `tbl_users.outlets` from the **database** rather than the `session_outlets` snapshot, so an assignment revoked mid-session stops being honoured immediately.

**Latent PHP 8 fatal closed in the same place.** The edge-case matrix showed Admin passing the check for a non-existent outlet id, which then hits `$outlet_details->id` on a NULL row. `canEnterOutlet()` therefore requires the outlet to exist, be Live and belong to the company **for everyone including Admin** — Admin being precisely who could reach an arbitrary id.

**Sales enforcement, two points.** `isSalesEnabledOutlet()` is checked in `Sale::__construct()` (scoped to the POS route) and again in `add_kitchen_sale_by_ajax()`. Deliberately **not** on `push_online()` or `add_sale_by_ajax_split()` — those complete orders that already exist, and blocking them would strand an order rather than prevent one, exactly the reasoning applied to the register gate.

**Two ordering/looping traps found and fixed during the build:**
1. *Guard placement.* The check started in `POS()`, but the constructor's register gate runs first — so at Central Store an Admin was bounced to `Register/openRegister`, shown the wrong message, and invited to open a register at a purchasing outlet. Moved ahead of the register gate.
2. *Infinite redirect loop.* Redirecting blocked users to `Authentication/userProfile` loops forever for **self-order sessions** and **`role == 'POS User'`**, both of which that method sends straight back to `Sale/POS` (Authentication.php:600-608 and :621). Those two cases now get the terminal message the controller already uses for a POS that must not open; everyone else gets the flash-and-redirect.

**Roles:** `view-67` + `enter-67` granted to Manager and Accountant (only Admin had them). Waiter, Cashier and Store Officer get neither, so Central Store is unreachable for them by list, by URL, and by login pinning. Note the pinning mechanism (Authentication.php:512-533): a non-Admin assigned to exactly **one** outlet is pinned to `tbl_users.outlet_id` at login and never sees the switcher at all.

### F2 — Outlet filtering on the stock screens — DONE
Outlet selector with an **All Outlets** mode added to the Inventory screen, the Inventory Alert List (which had no filter form at all) and the List Item screen; All Outlets added to the Stock Report, which already had a per-outlet selector from Phase B.

**"All Outlets" means "all outlets YOU can access", not all company outlets** — scoped through `getAccessibleOutletIds()`, DB-backed and consistent with `canEnterOutlet()`. A combined view that reached past a user's assignment would have handed back exactly what the F1 fix took away.

**Security fix — the Stock Report's outlet_id was unvalidated.** `Report::stockReport()` passed `$_POST['outlet_id']` straight into the ledger with no check, so posting another outlet's id returned that outlet's stock report. **This one was introduced by the Phase B stock report, not inherited from the vendor.** Now routed through `resolveOutletScope()`, which validates against the accessible list and silently falls back to the user's own outlet.

**Query changes:** 34 outlet predicates widened in `getInventory()` / `getInventoryAlertList()`, 14 in `getStockLedger()` / `getUnpostedStockImpact()`. The ledger's outlet `?` bind was replaced by an interpolated integer list (ids come from the DB as ints and are cast again by `outletScopeSqlList()`; date binds stay parameterised) because an IN list has variable arity and generating N placeholders across 11 sources would have made the bind order fragile. Verified **4 placeholders = 4 binds** on every source afterwards. `getCurrentInventory()`, `getInventoryFoodMenu()` and `checkInventory()` were deliberately left session-scoped — the first answers "how much is here right now" for the waste/adjustment forms, where the session outlet is the only sensible scope.

**Shared helper extraction (`stockClosingBalance()`).** The eleven-term closing-balance formula was written out by hand in **four** places — `getAlertCount()`, `Inventory_model::getCurrentInventory()`, the inventory view and the alert-list view. Four copies is how figures drift between screens, so it now lives once in my_helper.php and every caller uses it. The replacement matched the expression **in full**, so a copy that had already drifted would have failed to match and been reported rather than silently normalised into agreement — all four matched exactly, confirming no drift had occurred yet. Verified behaviour-preserving across 4 outlet scopes including **33 rows with NULL sums** (the common case): **0 mismatches**.

**List Item additions.** Investigation first established that an outlet filter on List Item had **nothing to filter on**: `tbl_ingredients` has zero outlet columns and there is no outlet↔item assignment table anywhere — every outlet-bearing table is a transaction table. The only candidate, an activity-based *visibility* filter, was rejected on measured data: Door Soft had activity on 8 of 8 items (filter appears to do nothing), KFC Zone 1 of 8, and **Central Store 0 of 8 — an empty item list at the very outlet where you go to find items to purchase**, a chicken-and-egg trap breaking the workflow Phase F exists to enable. It would also hide master data on the create/edit screen, where "this item doesn't exist for you" is a different and more dangerous claim than "this item hasn't moved here yet". So a **Stock Qty column** was added instead and the dropdown scopes *that column only* — the item list itself stays company-wide and is never hidden per outlet (commented in the view so nobody "fixes" it later). Stock is fetched by reusing `Inventory_model::getInventory()` rather than growing a fifth copy of the stock query.

### F3 — Committed stock (roadmap item 14) — DONE
Deduction already worked, but only at sale *completion*: consumption rows are written in `Save()`, `add_sale_by_ajax_split()` and `push_online()`, and **not** in `add_kitchen_sale_by_ajax()`. From placement until payment the ledger still counted the stock as on hand — in a lounge with tabs open for hours, a large persistent overstatement, and the real content of item 14.

**Approach taken: do NOT write consumption at placement.** Delete-and-reinsert on the completion paths, plus offline replay, makes double-counting a live hazard and would corrupt the audit ledger. Instead *committed* quantity is computed separately from `tbl_kitchen_sales_details`, expanded to ingredient level, with `available = closing − committed` — the same separation Phase B's `getUnpostedStockImpact()` already established. Verified across all three product-type branches of the consumption writer.

**Deliberately reproduced quirk.** The base product applies `del_status` inconsistently to running-order rows. Matching that inconsistency exactly was the only way to make committed stock agree with what the running-order screens themselves display. Correcting it here would have made the two disagree, which is worse than reproducing a known oddity. Flagged so nobody later "fixes" it in isolation.

### F4 — Oversale control (roadmap item 17) — DONE
`tbl_companies.allow_oversale` (global) + a per-item override with three states (0 = use global, 1 = always allow, 2 = always block). Both default to a no-op, so an installation that changes nothing behaves exactly as before. **`allow_oversale` defaults to 'Yes'** — live data already contains negative stock, so defaulting to 'No' would have blocked real items the moment the column landed.

**Defect found by this stage's own tests and fixed before shipping: the first implementation failed CLOSED.** Empty or unrecognised flag values resolved to "block", which would have stopped sales on any item whose flag had never been written — i.e. every existing item. The resolver now blocks only on an explicit `'No'`. Worth recording as a pattern: for a policy flag guarding a revenue path, failing open is the safer default, and the test that caught it was the one that fed in garbage rather than valid states.

### F5 — Zero-stock block (roadmap item 15) — DONE
Client check on both `.single_item` handlers via `window.items` (the single carrier read by both handlers regardless of which of the seven render sites drew the tile — the Phase D lesson), plus server enforcement in `add_kitchen_sale_by_ajax()`, both resolving policy through one F4 helper. Blocks on the **selling outlet's** stock only, per the corrected item 15 rule.

**The `''` vs `'0'` distinction is load-bearing.** An empty available-units value means *no recipe, therefore unconstrained*; `'0'` means *genuinely out of stock*. Conflating them would block every item that simply has no recipe defined. Stated explicitly in the implementation, not only here.

**Known limitation, stated up front:** `push_online_for_kitchen()` is fire-and-forget — the order is written to IndexedDB and rendered locally *before* the AJAX call — so a server-side block cannot fully prevent an oversold order, only refuse to persist it server-side. Identical to the register gate's limitation. The client check is the primary UX; the server check is the integrity backstop.

**Data-completeness limit, not a defect:** a food menu with no recipe consumes no stock and therefore can never be blocked. The block is only ever as complete as the recipes are. This is the single most likely reason a client reports that the block "isn't working".

### Phase F — variation inheritance (deferred, rule already decided)
Not built, but the rule is settled so it is not re-litigated: **the parent item holds the actual stock data, and variations draw from that same underlying stock.** Therefore a parent blocked from oversale must **win** over any variation set to "always allow" — a variation cannot be more permissive than the stock it consumes. Any future implementation must resolve parent-then-variation in that order, not the reverse.

### Phase F — deferred by decision
- **F6 (transfer gaps) — DEFERRED, not in Phase F.** Orthogonal to items 14/15/17. Two known gaps: (1) stock in transit is invisible — every ledger query filters `status = 1` (Received), so goods sitting at Draft/Sent are counted at neither end and there is no "in transit" figure anywhere; (2) `tbl_transfer_received_ingredients` is **read by five queries and written by none** — `saveTransferIngredients()` only ever writes `tbl_transfer_ingredients`, and the edit path *deletes* from the received table without repopulating it. The table is vestigial; the "received" concept is half-built in the schema. Also worth recording: the receiver must physically switch into the destination outlet to mark a transfer received — there is no incoming-transfers view from elsewhere.
- **Unit Selling Price on List Item — SHIPPED BUT CURRENTLY EMPTY.** `tbl_ingredients` has only `purchase_price` and `consumption_unit_cost`; **there is no selling-price column**. Selling price lives on `tbl_food_menus`. The implemented reading — a direct-sale product item (`is_direct_food = 2`) reaching its price via `tbl_ingredients.food_id → tbl_food_menus.sale_price` — is correct by design and needs no schema change, but renders **entirely blank on current data** (verified: 0 of 9 items resolve a price, because all are `is_direct_food = 1` with `food_id = NULL`). Recipe ingredients are never sold on their own, so blank is *correct* rather than missing. If a price on every item is wanted, that is a new `selling_price` column plus an item-form field — a migration, materially more than "a column that reads existing data".
- **Stock Value column — DEFERRED** to the List Item enhancement phase immediately after Phase F, together with bulk upload and List Food Menu search.

### Phase F — known pre-existing bug, flagged for the List Item enhancement phase
**The Inventory screen's grand-total valuation is wrong.** It builds a quantity by *string-concatenating* whole units and remainder rather than dividing:
```php
$total_stock_in_float = ((float)(((int)$total_sale_unit).".".((int)$totalStock%$conversion_rate)));
```
Test Coke, conversion rate 24, 110 consumption units: 4 whole + remainder 14 → `"4" . "." . "14"` = **4.14 bottles**, where the true figure is 110/24 = **4.583**. It understates here and *over*states when the remainder is a single digit (remainder 5 → 4.5 vs true 4.208). The **display** is fine — "4 Bottle 14 Pcs" is correct — only the valuation float is broken. Deliberately **not fixed during Phase F**: it is a visible figure that may have been reconciled against, and it will be corrected as part of building the Stock Value columns, which is the exact moment the formula has to be right. Fixing it now in isolation would mean touching it twice. **Any future Stock Value column must not inherit it.**

## Payment Writer Fix — `push_online()` — DONE (out-of-phase, critical)
*(Base-product defect, confirmed byte-identical to vendor source. Given its own stage at F1–F5 rigor because it writes live financial data on every completed sale.)*

**Correction to the original write-up:** the `getPaymentInfo()` guard is inside `push_online()` itself (Sale.php ~2574/2592), **not** in `update_order_status_ajax()`. That latter method is separate and correctly written (unconditional delete-then-rewrite, no hardcoding). The whole defect is self-contained in one method.

**Write-path inventory (verified three independent ways):** `Sale.php` is the **only** file in the entire application that writes `tbl_sale_payments` (10 sites). All 27 `Report_model`, 12 `Sale_model`, 9 `Dashboard_model` and 11 `my_helper` references are reads. `libraries`, `hooks`, `core` and `third_party` contain none.

**Trigger:** a Live `tbl_sales` row already exists with the same `sale_no` (`getSaleDetailsBySaleNo()` filters on `sale_no` + `del_status` only — no outlet or company scoping). Two callers reach it with **different payloads**, producing two distinct failure modes:

- **Mode A — re-sync** (`push_online()` on a 10s interval, or `push_online_sync()`). Payload *has* `payment_object`. The update branch inserted a hardcoded `payment_id=1`/`"Cash"` row for the full `total_payable`; the guard at 2592 only looks for the *same* `payment_id`, so it could never see or remove that row. Result for a non-Cash sale: **two rows, revenue double-counted** in payment breakdowns, Z-report and register reconciliation. Masked when the real method genuinely is Cash — which is why only some sales showed it.
- **Mode B — editing an existing paid sale** (`push_online_update()`, `pos_script_v7.3.js:8939`, fired whenever `edit_sale_id` is set). **That payload carries no payment fields at all** — no `payment_object`, no `payment_method_type`, no `paid_amount`, no `due_amount` (builder at `pos_script_v7.3.js:8635-8690` simply never emits them). So the delete at 2360 destroyed the real rows, the hardcoded Cash row replaced them, the real writer never ran (`isset($order_details->payment_object)` is false), and `paid_amount` / `due_amount` / `payment_method_id` were written as `0` from `trim_checker()` on absent fields (`sql_mode` is empty, so `''` coerces silently). **A Bank Transfer sale becomes a Cash sale, and the totals still reconcile** — so the "do payments sum to the total?" check cannot detect it. **Confirmed to have actually fired in production on two sales**, hard-deleting their real POS and Bank Transfer tenders with no recovery trail.

**Why the naive fix would have been worse:** simply deleting the hardcoded insert leaves Mode B with the delete at 2360 still firing and nothing rewriting — the sale ends with **zero** payment rows. The delete had to go too.

**Fix applied.** The update branch no longer deletes payment rows and no longer inserts the hardcoded Cash row; the pre-writer delete now fires only when `$ir_has_payment_payload` is true; and on the edit path `payment_method_id` / `paid_amount` / `due_amount` are dropped from the update array so stored values survive.

**Decision B1 (client), and the wiring it needed.** On an edit, preserve the payment record as-is; **never auto-rescale** — an edit is not a re-tender, and post-payment edits are rare and Manager/Admin-only. B1 alone was **not sufficient**: due is driven **entirely** by `tbl_sales.due_amount` — `Customer_due_receive_model::getCustomerDue()` is `SUM(tbl_sales.due_amount) − SUM(tbl_customer_due_receives.amount)`, and the Customer Due Report (`Report_model:2097`), Customer Ledger (`:2422-2428`) and the R3 Due filter (`:1790-1794`) all read the same column. Since the edit path blanks it, the fix **recomputes `paid_amount` from the surviving payment rows and sets `due_amount = total_payable − paid_amount`**. That is what routes a post-edit shortfall into the existing Customer Due Receive flow instead of fabricating a payment.

**Negative due is deliberately NOT clamped.** If an edit lowers a total below what was already paid, `due_amount` goes negative — a genuine customer credit, and what `getCustomerDue()` should see. Clamping would silently discard money owed to the customer. Due reports filter `due_amount > 0` and ignore it, so it is currently *correct but invisible*; surfacing it is queued with the due-payment visibility batch.

**Verification (31/31 across three stages), on a clone with a separate app tree and a hard interlock, driving the real controller over HTTP:** both modes reproduced before the fix and gone after; the Cash control case unaffected; the insert path unchanged; replaying all stored payloads leaves payment rows identical to baseline; payment total unchanged; Z-Report, Register Report and all four R6 popups hash-identical; register 1's stored `{"Cash":8127}` snapshot untouched. The production file was verified **byte-identical** (md5) to the build that passed.

**Two related defects deliberately NOT bundled:**
- **`tbl_sales.payment_method_id` is written as Cash for essentially every sale.** Line 2334 reads `$order_details->payment_method_type`, sourced from the `#finalie_order_payment_method` select — separate from the tender UI that builds `payment_object`. Checked across eight stored payloads: it is `"1"` in every one, including sales genuinely tendered as Credit Card (2), Bank Transfer (4) and POS (57). **This affects the insert path too**, so the column is unreliable for nearly every sale, and it drives the payment-method summary reports (`Report_model` 377-411, 2308) and dashboard `getSalePaidAmount()`. Consequence: after this fix a re-sync writes correct payment *rows* but still a wrong *header* column. Own stage, plus a backfill decision.
- **Customer Due Receive structural limits:** `tbl_customer_due_receives` has **no `sale_id`**, so collection is customer-level, not invoice-level; and `getCustomerDue()` is **outlet-scoped**, so a due raised at one outlet is not collectable at another. Both are base-product design, recorded for the due-payment visibility batch.

### Waiter "Place Order" completely non-functional — two rounds, two different root causes

## Technical Reference Notes (from Claude Code DB exploration)
- Project: `C:\wamp64\www\rexlio` — CodeIgniter 3 app (iRestora PLUS v7.5)
- Database: `rexlio` on localhost, `tbl_` prefix, 83+ tables (Phase D additions: tbl_price_tiers new; price_tier column added to tbl_kitchen_sales, tbl_sales, tbl_holds; default_price_tier added to tbl_counters. Phase F additions: `is_sales_enabled` on tbl_outlets; Central Store created as **outlet id 4**)
- **Outlet access is enforced in two independent places, and both matter.** `tbl_users.outlets` (CSV) decides which outlets a user may enter — checked by `canEnterOutlet()` against the *database*, not the `session_outlets` login snapshot. `tbl_outlets.is_sales_enabled` decides whether anyone may sell from an outlet at all, whoever they are. Central Store uses both: assigned only to Admin/Manager/Accountant, and `is_sales_enabled = 0` so even an Admin standing in it cannot take an order. Note `tbl_outlets.active_status` is **not** an access control — it is consulted only at login to pick a default outlet, and marking an outlet inactive does not hide it from the switcher.
- **Stock arithmetic lives in exactly one place: `stockClosingBalance()` (my_helper.php).** Before Phase F the eleven-term formula was written out by hand in four locations. Do not re-inline it. Callers pass a row from any of the `Inventory_model` stock queries, all of which expose the same sum aliases.
- Items: `tbl_food_menus` (core sellable item table) — pricing columns: sale_price (Regular), sale_price_take_away (Outlet), sale_price_delivery, sale_price_vip, sale_price_club (new)
- Ingredients: `tbl_ingredients`, linked via `tbl_food_menus_ingredients` — mixed table (see Phase E note above). **UI now calls these "Items"** (Phase E rename); the table, columns and stored values are unchanged.
- **`tbl_ingredients.ing_type` stores the literal string `'Plain Ingredient'` as DATA, not as a label.** Used in WHERE clauses at 7 sites — `Ingredient.php:87` and `Purchase_model.php:40` (data filters: breaking them silently empties the item list and the purchase item picker) plus five per-row display branches in `inventory.php`, `inventoryAlertList.php` and `inventoryReport.php`. Never rename it for UI consistency. The Phase E rename was confined to `lang()` values for exactly this reason.
- Known minor issue: `$lang['ingredient_category']` is defined twice in `english_lang.php` (lines 444 and 605); PHP takes the last, so line 444 is dead. Pre-existing, harmless, worth tidying sometime.
- Stock: no single stock table — computed ledger from `tbl_purchase`, `tbl_sale_consumptions*`, `tbl_wastes`, `tbl_inventory_adjustment`, `tbl_transfer*`
- Orders: `tbl_sales` / `tbl_sales_details` — **only populated on completed/invoiced orders**, and only reliably since the Phase C push_online() sync fix (see Phase C notes above); running/uninvoiced orders live in `tbl_kitchen_sales` (server-side, populated at placement) and browser IndexedDB `sales` store (device-local, authoritative for in-progress editing); table status derived from `tbl_kitchen_sales` + `tbl_orders_table`, not from tbl_sales
- Print/invoice: settings in `tbl_companies` (not `tbl_settings`); templates in `print_invoice.php`, `print_invoice_56mm.php`, `print_invoice_56mm_public.php`; ESC/POS bridge in `print_server/`
- Access control: role-based access is snapshotted into session (`function_access`) at login — new screens require re-login to appear in the menu for already-logged-in users
- Data quality notes: several date columns across the schema (`tbl_purchase.date`, `tbl_transfer.date`, `tbl_production.date`, `tbl_sales.sale_date`) are stored as varchar, not DATE — consistently Y-m-d formatted so comparisons work, but fragile; cancelled/voided orders are hard-deleted (not soft-deleted), so their stock impact is not recoverable after cancellation
- Known base-product bug fixed: push_online()/push_online_sync() unguarded JSON.parse causing silent, total sync failure — see Phase C notes. This was present in the base iRestora PLUS product, not introduced by any Rexlio modification.
- **Known base-product gap fixed: sales could be taken with no register open.** Two separate defects, both confirmed against the vendor's original `Sale.php` (extracted from `update_code.zip` in the nulled package — the guard is byte-identical, so this is iRestora PLUS's own design, not a Rexlio regression):
  1. *Waiters bypassed the register check entirely.* `Sale::__construct()` wrapped the check in `if($designation!="Waiter" && ...)`, so any user with designation "Waiter" could open the sale screen and place orders with no register open anywhere. Fixed by checking waiters too, against a deliberately different rule: a waiter never opens a register of their own, so requiring one would block them permanently — they are allowed to trade while **any** register is open at their outlet (`Common_model::isAnyRegisterOpenForOutlet()`, new). Cashiers/admins keep the original per-user `isOpenRegister()` call unchanged, including its side effect of restoring counter/printer session data. The food-court and online-order exemptions were left exactly as the vendor had them (deliberately out of scope).
  2. *The check was UI-only.* It existed solely in the sale-screen constructor; `add_kitchen_sale_by_ajax()` (writes tbl_kitchen_sales at placement) and `push_online()` (writes tbl_sales at completion) had **no register check at all**, for any role — so a tab left open when a register closed carried on saving orders, and a direct POST bypassed the gate completely. Fixed by adding `canPersistOrderNow()` (my_helper.php) to **placement only**. It reuses the existing `invoice_status`/`invoice_msg` response shape, which the POS already surfaces as a toast error, so no client change was needed. **`push_online()` is deliberately NOT gated:** it syncs an order that already exists in device IndexedDB, so blocking it would not prevent the sale (it already happened) — it would only strand it unsynced until a register reopened, creating exactly the kind of silent backlog the Phase C fix eliminated. Late completions are allowed through on purpose; new orders are stopped at creation.
- **Known base-product gap fixed: anyone could open a register.** The `Register` controller had no access check of any kind — its constructor verified login and outlet only, and neither `openRegister()` (the form) nor `addBalance()` / `addExistingBalance()` (which insert into tbl_register) called `checkAccess()`. There was also no tbl_access row to gate it with; the only register-adjacent rows were id 94 (`pos_21`/close_register, a POS button permission) and id 159 (register_report, a report). Fixed by adding the missing permission — tbl_access 376 (`register`) / 377 (`open`, token `open-376`) — and gating the three entry points, so it is toggleable per role rather than a hardcoded role-name check. Granted by default to Admin/Manager/Cashier; denied to Waiter/Store Officer/Accountant (neither of the latter two handles the till, and an accountant opening a register would muddy the session they audit). Related UX fix: `Sale::__construct()` previously redirected anyone without an open register to `Register/openRegister`; for a user who now lacks that permission this would land on a "not permitted" error, so they are redirected to their profile with `register_not_open_ask_manager` instead.
- **`Custom::encrypt_decrypt()` is a no-op passthrough — the "encrypted id" pattern protects nothing, anywhere.** `application/libraries/Custom.php` returns its argument unchanged for both `encrypt` and `decrypt`. Every controller that decrypts a URL id and fetches by it without an ownership check is therefore equally exposed — Transfer, Purchase, FoodMenu, Ingredient, Outlet and others. **Provenance established:** the running file is byte-identical (MD5 `0f4f245705e0b3efca9652386e39be61`) to the vendor package's copy, the v7.5 `update_code.zip` ships no replacement for it, and it carries the same release timestamp as every other file in `libraries/`. Evidence points to vendor design rather than a nulling artifact — neutering it buys a pirate nothing (it is URL-parameter obfuscation, not licence verification; the real licence surface is the `str_rot13` `language_manifesto` flags and the `isServiceAccess*()` family), the code's shape is authored rather than stubbed (argument guard, both branches symmetric, trailing `return FALSE` with an explanatory comment), and nothing else in `libraries/` is gutted. **Caveat: only the nulled distribution was available, so this could not be diffed against a licensed original.** Phase F fixed only `setOutletSession()`, because Central Store depended on it; the systemic gap is deliberately left open and recorded here.
- **The consumption writer's recipe lookups have no `del_status` filter.** `Sale.php:2353`, `:2369` and `:2388` query `tbl_food_menus_ingredients` / `tbl_ingredients` with no `del_status` predicate, so a soft-deleted recipe line still consumes stock. Latent today (zero soft-deleted recipe rows). The F3 committed-stock query **deliberately reproduces this omission** so that committed and actual consumption reconcile — if the two rules disagree, available stock drifts permanently. Fix both together or neither.
- **A food menu with no recipe consumes no stock and can never be blocked.** Items with no rows in `tbl_food_menus_ingredients` (currently Cup Yogurt, Juice, Water) are sellable but stock-invisible; the join correctly drops them. The F5 zero-stock block will be a silent no-op for every such item — **the block is only as complete as the recipes are.**
- **Live data already contains negative stock** (Test Water and Coke were both negative at outlet 1 before Phase F). Oversale has already happened in practice. This is why `allow_oversale` must default to `'Yes'` — defaulting to `'No'` would block real items the moment the column lands.
- Known minor issue: `getInventoryAlertList()` contains a **duplicated `total_production` subquery** (two identical aliases in the same SELECT). Pre-existing vendor duplicate — identical value, second alias wins, harmless. Surfaced when the F2 rewrite counted 12 outlet predicates where 11 were expected.
