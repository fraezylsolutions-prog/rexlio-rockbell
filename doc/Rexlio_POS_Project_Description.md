# Project: Rexlio POS

Rexlio POS is a restaurant, lounge, and hospitality management platform built on the iRestora PLUS Multi Outlet CodeIgniter/MySQL script (originally a CodeCanyon script, now being rebranded and extended as "Rexlio"). The base system already includes offline-first sync, multi-outlet support, table/kitchen management, and a web-based Waiter Panel.

## Current Status Summary (see Modification Roadmap for full detail)
- **Phase A (Quick Wins):** Done
- **Phase B (Filters & Reporting):** Done
- **Phase C (Running Order + Table screens):** Done — included discovering and fixing a significant pre-existing base-product bug where completed orders were never syncing to the server at all (a defect in iRestora PLUS itself, not introduced by Rexlio work), which also means the product's sales reports now reflect real data going forward.
- **Phase D (VIP/Club Pricing Tiers):** DONE — built, tested, and confirmed working end-to-end, including a layout regression found and fixed during the work (see Modification Roadmap). **VIP and Club are now two independent tiers**, each with its own sale-screen button and its own price field on the Food Menu form (`sale_price_vip` / `sale_price_club`). It first shipped as a single combined "VIP|Club" button as a deliberate scope simplification, then split once the client committed to them as genuinely distinct tiers. Counter-level default tier is also complete: a dropdown on counter add/edit which additionally **locks** the whole order-type row for ordinary staff at any counter set to a non-Regular tier, with Admin/Manager override. The key architectural decision was introducing `price_tier` as a field separate from `order_type`, so VIP/Club orders record as ordinary dine-in orders and every existing table-gating, invoice, KOT and reporting path needed zero changes.

  Open items carried out of Phase D — none is a defect:
  - **A tier with no prices entered sells at Regular prices.** This is the designed fallback (an unset or zero tier price falls back to the Regular price, matching how take-away and delivery already behave). It is worth knowing because it makes a tier look inert: a Club counter locked correctly but with no `sale_price_club` values will price exactly like Regular. **Enter at least one price per tier before any client demo or handoff.** This is precisely what made a working Club lock look broken during testing — see the corrected diagnosis in the Modification Roadmap.
  - **French, Spanish, and Arabic language files still carry the old "Dine In"/"Take Away" wording** (`Dîner dans`, `À emporter`, and their equivalents). Deliberately left untranslated: "Regular" and "Outlet" are client terminology choices rather than literal translations, so the wording for each language is a human decision, not something to auto-translate. English is fully renamed. The newer `vip`, `club` and tier-lock strings were added to all four files but carry English values in the non-English ones.
  - **Per-client configurable tier labels** remain a Nuvora concern — the combined "VIP|Club" label that existed to sidestep this is gone, replaced by plain `vip` / `club` strings.
  - **Two design/robustness items deliberately left open:** wiring up the dead `setHeightInComponent()` as the durable fix for the sale-screen button-row layout fragility (the row now holds 6 buttons against a hardcoded 6-column grid; a 7th reproduces the footer bug), and the "layered vs replace" question of whether a price tier should display alongside the fulfilment type rather than replacing which button is highlighted.
  - **Dropped by decision, not forgotten:** the admin UI to toggle individual price tiers on/off. The counter-lock design replaced it — a client who doesn't use a tier simply never assigns it to a counter, so the counter list is the practical on/off control. `tbl_price_tiers.is_active` still exists and is honoured, so a system-wide switch remains available if ever needed.
- **Register access controls (out-of-phase priority fix):** Done. Two base-product gaps with accounting consequences, both confirmed against the vendor's original source and fixed: (1) waiters could take orders with **no register open at all** — the vendor's register check explicitly excluded them, and the check was UI-only, so any open tab kept saving orders after a register closed; (2) **any logged-in user could open a register**, waiters included — the Register controller had no access check and no permission row existed to gate it with. Order placement is now blocked server-side when no register is open (late completions of already-placed orders still sync, deliberately), and register-opening is now a proper toggleable permission (`open-376`) granted to Admin/Manager/Cashier by default. See Modification Roadmap → Technical Reference Notes for full detail.
- **Role & permission matrix:** Done. Six roles created (Admin, Manager, Cashier, Waiter, Store Officer, Accountant) with recommended permission sets applied. Note the existing `cashier` role was renamed to `Cashier` and re-granted rather than duplicated, so users already assigned to it kept working. Admin privilege still derives from `tbl_users.role = 'Admin'`, which short-circuits `checkAccess()` regardless of role_id.
- **Phase E (Ingredient → Item rename):** DONE. "Ingredient" is now "Item" throughout the UI — the core item screens plus embedded labels across purchases, waste, transfers, adjustments, recipes and reports (31 language values). A split-aware alternative (label is_direct_food=2 rows "Item" and is_direct_food=1 rows "Ingredient") was costed and rejected: only 4–5 of the 46 affected view files have per-row type data to branch on, so it would have been strictly more work for a *less* consistent vocabulary, and the precision it aimed at already exists in the Phase B Type filter (Ingredient / Product), which was left untouched. The rename was confined strictly to `lang()` values because `tbl_ingredients.ing_type` stores the literal string `'Plain Ingredient'` as data across 7 usage sites — two of them query filters that would have silently emptied the item list and the purchase picker had a blind find-and-replace been used. One tooltip was deliberately left un-renamed where "ingredients" means recipe components rather than the screen label. French/Spanish/Arabic keep the old wording pending human translation.
- **Phase F (Store & Stock Structural Foundation):** DONE — F0 through F5 complete and confirmed working. F6 (transfer gaps) deferred by decision, documented as a known gap.

  The foundational decision was to make **Central Store a dedicated Outlet rather than a new "Store" concept**. Outlets already carry everything a store needs — purchases bind to them, transfers move between them, the stock ledger is scoped by them — so building a parallel concept would have duplicated all of it. Central purchasing is deliberately **optional, not forced**: outlets keep the ability to purchase directly, because forcing everything through Central Store would turn every ad-hoc purchase into two documents and make the transfer-receipt step load-bearing daily when that step currently has no reminder or incoming-transfer view at all.

  One roadmap rule was **corrected** in the process: item 15 originally said to block a sale when *either* the main store or the counter's stock is zero. It is now block only when the **selling outlet's own** stock is zero — Central Store running dry must not stop a bar selling stock it already holds.

  - **F1 (Central Store + outlet access):** Done. Central Store exists as an outlet that cannot sell, enforced both on the sale screen and at the order-write endpoint. Two security issues were fixed on the way: **any user able to reach the outlet switcher could previously enter any outlet in the company by editing the URL** (the outlet list was filtered but the entry point was not, and the product's "encryption" of ids is a no-op passthrough), and a latent PHP 8 crash on a non-existent outlet id. Manager and Accountant gained outlet-switching rights; Waiter, Cashier and Store Officer cannot reach Central Store by any route. 16 stranded test orders left over from earlier phases were cleared first, through the product's own cancellation path with a full audit-log trail, because they would have corrupted the first real test of the F3 stock work.
  - **F2 (Outlet filtering on stock screens):** Done. Inventory, Stock Report, Alert List and List Item all gained an outlet selector with an **All Outlets** combined mode, scoped to the outlets each user may actually access — a combined view reaching past a user's assignment would have given back exactly what F1 closed. A second security fix landed here: the Stock Report accepted an outlet id from the browser with no validation, so anyone could read any outlet's stock report. **That one was introduced by our own Phase B work, not inherited from the base product.** The eleven-term stock formula, previously written out by hand in four separate places, was consolidated into a single shared function — verified to produce identical results everywhere before and after.

  - **F3 (Committed stock):** Done. The central design question — whether to physically deduct stock the moment an order is placed — was resolved as **no**. Stock in this product is not a stored balance but a figure computed on demand from eleven correlated ledger terms, so a real-time deduction would have meant inventing a running balance the rest of the system does not have, and every cancellation, edit or failed sync would then need to unwind it correctly. Instead, stock already committed to running orders is **calculated** and subtracted from what the sale screen treats as available. The result is the same protection with no new state to keep consistent. A quirk of the base product was reproduced deliberately rather than corrected here: the way `del_status` is applied to running-order rows is inconsistent, and matching it exactly was the only way to make committed stock agree with what the running-order screens themselves show.
  - **F4 (Oversale control):** Done. Two levels: a global default, plus a per-item override with three states (follow the default, always allow, never allow). The default is a genuine no-op — an installation that changes nothing behaves exactly as before. One defect was found by the stage's own tests and fixed before it shipped: the first implementation **failed closed**, treating an empty or unrecognised setting as "block", which would have stopped sales on any item whose flag had never been written. It now blocks only on an explicit "No".
  - **F5 (Zero-stock block):** Done. Enforced on both the sale screen and the server, so it cannot be bypassed by a stale page or a direct request. It blocks on the **selling outlet's** stock only, per the corrected rule above. The implementation distinguishes carefully between "this item has no recipe, so it is unconstrained" and "this item is genuinely out of stock" — conflating the two would have blocked every item that simply has no recipe defined.

  **Variation inheritance is deferred, with the rule already decided** so it is not re-litigated later: the parent item holds the actual stock, and variations draw from that same stock, so a parent blocked from oversale must win over any variation set to "always allow". A variation cannot be more permissive than the stock it consumes.

  Deferred by decision, with reasons recorded in the Modification Roadmap: the transfer-system gaps (stock "in transit" is invisible to every screen, and one transfer table is read by five queries but written by none), the Stock Value column, and a **known pre-existing valuation bug** — the Inventory screen's grand total builds a quantity by string-concatenating whole units and remainder instead of dividing, so it can be materially wrong in either direction. It is deliberately left alone until the Stock Value columns are built immediately after Phase F, which is the exact moment the formula has to be correct; fixing it now would mean touching it twice.

  Still true now that F5 has landed: **a food menu with no recipe consumes no stock and therefore can never be blocked** — the zero-stock block is only ever as complete as the recipes are. This is a data-completeness limit, not a defect, and it is the single most likely reason a client reports that the block "isn't working".
- **Reporting enhancements batch (R1–R6):** DONE. Six reporting-only improvements, held strictly to reporting scope: column visibility on report screens, a shared invoice-detail popup on the Sale No, gaps closed on the Detailed Sale Report (invoice-number search, a Due filter that previously returned paid sales, All Outlets, and a Payment Method filter), the Sales by Category report with User and Time Range filters, sidebar entries plus a new Order Lookup screen presenting running and completed orders together, and a read-only detail popup on the Register Report.

  Three things are worth carrying forward from this batch:

  - **The report screens run on two different table-library builds.** Twenty-five screens use one build and six use a newer one, and only the newer one ships the column-visibility control. Adding that control uniformly would have thrown an error and stopped the table from rendering at all on the twenty-five older screens, so it is applied only where the loaded build actually supports it. Consolidating onto one build is queued as its own stage — it changes the table library under two dozen live report screens and is not a drive-by change.
  - **The Register Report popup deliberately does not reuse the register-closing calculation.** It is a separate read-only query, so viewing a register that is currently open cannot disturb it. It shows the figure derived from current data alongside the figure recorded when the register was closed, because the two can legitimately differ and a visible, labelled difference is better than a silent mismatch. Two limits are stated in the popup itself rather than buried in documentation: registers whose time windows overlap cannot be told apart by any key the data actually has, and expenses, purchases, due receipts and supplier payments are recorded by date rather than by time, so a register covering part of a day shows whole-day figures for those four.
  - **There is no "brand" concept anywhere in this product**, so the category breakdown stands in for the brand breakdown the reference layout showed. Similarly, "Total Refund" in that layout maps to cancelled orders here, and "Business Location" maps to Outlet.

  One item originally in this batch — an auto-print investigation — was dropped after the client resolved it independently.

- **Payment-writer fix (out-of-phase, critical):** DONE. A base-product defect with direct financial consequences, found while testing the reporting batch and confirmed against the vendor's original source. When an order that already exists on the server is pushed again, the sync routine deleted the order's payment records and wrote a **hardcoded Cash payment for the full amount**, regardless of how the customer actually paid. It reached that state two different ways, and the second was not obvious:

  - **A completed sale re-syncing** (for example after a dropped connection loses the response, so the device retries) ended up with **both** the fake Cash record and the real one — the revenue counted twice in payment breakdowns, the Z-report and register reconciliation. This was masked whenever the real payment genuinely was Cash, which is why only some sales showed it.
  - **Editing an already-paid order** was worse. That path sends no payment information at all, so the real payment records were deleted and only the fake Cash one remained: **a Bank Transfer or card sale silently became a Cash sale.** The order total still matched, so the usual "do the payments add up?" check could never catch it. This was confirmed to have actually happened to two live orders during the project.

  The fix stops the sync routine from touching payment records unless the request actually carries replacement payment data. Where it does, the real payment is written once. Where it does not — the edit case — the existing payment record is **left exactly as it is**. The deliberate choice here was **not** to rescale a payment to match an edited total: an edit is not a re-payment, and inventing one would be fabricating a financial record. Instead, if an edit raises an order's total, the difference is written as an amount **due**, which routes it into the product's existing Customer Due Receive workflow — the normal way outstanding money is collected. That connection needed one extra piece of wiring to work: every due screen and report in the product reads a single field on the order, and the edit path had been blanking it.

  Verified against a copy of the live database before release, driving the real code, with both failure modes reproduced beforehand and gone afterwards, and with every existing order replayed to confirm nothing else moved. Two related items are queued rather than bundled: the order's summary "payment method" field is separately unreliable (it is written as Cash for essentially every sale, from a dropdown that is not the one the cashier actually tenders with), and customer credits — which can now arise if an edit *lowers* a total below what was already paid — are recorded correctly but not yet surfaced anywhere the user can see.

- **Live Launch Batch (2026-09-03 → 09-08):** DONE. Everything driven by the run-up to real business use on `rockbell.fraezyl.app`. Grouped by date rather than phase because it was reactive work.

  - **Live deployment — the installer is not optional.** Standing up the host by copying files and importing a database dump produced a blank page / 501. Two theories were chased and both were wrong (a `base_url` fallback problem, and a missing `index.php`). The real cause: this product **requires the vendor's own `/install` process**, which generates state a raw copy cannot produce, and it fails looking like a server fault rather than a missing-installation fault. (The state was reported as `assets/bluezimp/` — absent and untracked locally, which fits, but `bluezimp` appears nowhere in the application code, so that specific path is recorded as unverified. The rule holds regardless.) Resolved by a fresh deploy through the installer, and **written up as a standing procedure for all future client deployments in `DEPLOYMENT.md`** — never manually copy-and-configure a raw dump.
  - **Waiter "Place Order" completely non-functional** — the most serious defect of the batch, and it took two rounds. Waiters could not place orders on **any** order type (first incorrectly scoped to Club only). Round 1 fixed 29 unguarded select2 calls that crashed because the Waiter view renders `#select_waiter` as a hidden input. Round 2 found three *more* unguarded calls sitting earlier in the same handler, whose real cause was **two independent flags that disagree** — the view branches on `designation=='Waiter'`, the JS branched on the `is_waiter` session flag, and production waiters are `designation='Waiter'` with `is_waiter='No'`, so they got the hidden input *and* the select2 path. **Round 1's testing missed it because the test fixture was built to satisfy the feature's happy path rather than to match production**, so it validated the wrong shape. Fixed with a helper that tests the element rather than a flag. A self-introduced regression (a dropped `customer_name` declaration) was caught before deploy by a line-by-line diff audit, not by a test.
  - **Admin Register Management (force-close):** view all open registers and close one on someone else's behalf. The central decision: the admin **manually types the counted cash** beside the system-computed figure — deliberately not a one-click accept, which would destroy the discrepancy-catching purpose of closing a register. New `tbl_register` columns (`system_closing_balance`, `force_closed_by`, `force_close_reason`), a configurable `manage_registers` permission, full audit logging, and an admin cannot force-close their own register. Three pre-existing bugs were found by running it rather than reading it. **Two process lessons came out of its rollout:** a sidebar entry can be correct in the view and still invisible, because menu items are filtered client-side against a login-time permission snapshot — which applies to Admin too, and which re-login cannot fix if the underlying row is missing; and the permission was "verified" against a test session whose grants differed from the real Admin account, masking that it had never been granted in production. The lesson recorded at the time: **"verified" must name the database it was verified against.**
  - **Cashier Running Order visibility:** a cashier holding the running-orders permission saw an empty list. The screen gate was one part; the real cause was that the list was scoped by a **hardcoded role-name list** naming two roles — 'Leader' and 'Sales Supervisor' — that **do not exist in this database**, so only Admin ever saw the full list and every other role silently saw only its own orders. Now permission-driven and role-agnostic, with the duplicate rule removed from the model. Outlet scoping was deliberately left alone; widening it would let a cashier bill another venue's order.
  - **Category rail redesign:** bigger, raised buttons with a 56px minimum height (clearing the 44px touch-target guideline the previous 30px rail missed), and labels at 17px/800 that wrap rather than truncate. The requested weight had to be explicitly loaded — the app's Montserrat import stops at 700, so 800 would otherwise have been a synthesised fake-bold. Width deliberately unchanged. Knowingly supersedes an earlier decision that had kept the rail short so more categories fit; the trade (roughly 11–12 of 23 visible instead of 22) was accepted explicitly.
  - **Report enhancements:** a Waiter filter on Sales by Category, and a time-of-day filter on the Detailed Sale Report. The latter surfaced **a gate bug** — that report returns nothing unless one of a fixed set of filters is set, so a time-only search would have returned an empty report with no error, indistinguishable from "no sales in that window".
  - **Live data reset for launch:** sales, transaction data, registers and users cleared; Food Menu, Outlets, Settings, Roles and the full permission structure preserved. **Hard delete was chosen on evidence:** two of four reports checked do not filter `del_status`, so soft-deleted sales would have vanished from two reports while still counting as revenue in the other two — and six affected tables have no `del_status` column at all. That analysis surfaced a **pre-existing, still-unfixed bug**: sales voided through the UI still count as revenue in those two reports.
  - **Google Map on the frontend:** configured via the existing `tbl_companies.google_map` setting — no code change; the views have carried the embed since the baseline. **Flagged as likely broken and unverified:** the views render it as `<iframe src="…">`, expecting a bare URL, but the stored value is a full HTML-escaped `<iframe>` snippet, which cannot work as a `src`.
  - **Deferred out of this batch:** the waiter's own order history on their profile/dashboard (needs a new screen, its own permission and therefore its own migration and re-login cycle), and making the six Running Order actions work inline instead of deep-linking into the POS. On the latter, the assessment is recorded rather than assumed: Order Details and Re-print KOT are genuinely feasible inline, Cancel Order is borderline, and Modify/Invoice/Bill are hard because the order's authoritative state is device-bound IndexedDB.

## Working Notes

- Dev environment: WampServer locally, CodeIgniter/PHP/MySQL stack (not Laravel). Claude Code Desktop used for implementation, connected directly to the project folder and local MySQL database.
- Always check the uploaded iRestora PLUS documentation before assuming a feature needs to be built from scratch — several requested features (offline sync, waiter panel) already exist in the base script.
- Session/access caveat: any newly registered screen (new tbl_access row) is invisible to already-logged-in users until they log out and back in — access lists are snapshotted at login (function_access session data), not live-checked. Relevant for staff rollout later. **This bit twice during the Live Launch Batch, and the sharper version of the rule is: menu items are removed client-side by string-matching that snapshot, so a menu entry can be perfectly correct in the view and still invisible; it applies to Admin as well, despite Admin bypassing `checkAccess()` server-side; and re-login cannot help if the `tbl_access` row itself is missing — only a migration can.** When a new menu entry does not appear, check the database before touching the view.
- **Never stand up a new host by copying files and importing a dump — always run the vendor's `/install` first.** The installer generates state that is not in the repository and cannot be copied, and its absence fails as a blank page / 501 that looks like a server or routing fault. This cost a long misdiagnosis chase on the Rockbell deployment. Full standing procedure in `DEPLOYMENT.md`.
- **"Verified" must name the database it was verified against.** A component proof against the scratch clone is not evidence about production. This was learned the expensive way twice in the Live Launch Batch: a permission "verified" on a test session whose grants differed from the real account, and a menu item "verified" present while the production database lacked the row it depended on. Related: a test fixture built to satisfy a feature's happy path rather than to match production will validate the wrong shape — that is precisely how the waiter crash survived its first fix.
- Vendor update risk: the deeper this gets customized, the less likely future iRestora PLUS vendor updates will apply cleanly. Accepted tradeoff — Rexlio is expected to be maintained independently going forward.
- Existing hotel SaaS (iLodge) already exists in the wider product portfolio — worth revisiting later whether deeper hotel functionality (beyond the basic add-on) is better served by integration with iLodge rather than duplicating hotel logic inside Rexlio.
- Base-product defects discovered and fixed during this work should be tracked separately from Rexlio-specific customization, in case of any future decision to report them upstream or reconcile against vendor updates — currently documented inline in the Modification Roadmap's Technical Reference Notes section.
- Rexlio is explicitly understood as a temporary/interim product for the current client, pending completion of the larger modular Nuvora platform — this framing has already shaped at least one concrete decision (the VIP|Club combined label in Phase D) and should be kept in mind for future scope calls: favor the lower-effort, lower-risk option when a feature might later be superseded by Nuvora's more complete version.
