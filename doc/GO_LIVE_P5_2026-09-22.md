# Go-live runbook — P5 completion fix (+ everything since the last deploy)

Prepared 2026-09-22 for the owner to run. Claude runs nothing against live (`DEPLOYMENT.md`).

**Why this deploy is urgent:** on live today, every sale a Waiter invoices fails to record (HTTP 500 on the
completion sync, silent on the till). Those sales are queued on the waiters' devices and upload by themselves
once step 4 is done. **Until then nobody clears browser data or resets a waiter till.**

Local HEAD: `e9a34e01`. Live was verified (read-only probes, 2026-09-21) to carry the code of `3457253b`
(H11 + docs). Everything between is in this deploy: P1, P3, P2, P4, P5-1/2/3, the logging setting.
Replace `<user>`, `<livedb>`, `<cpaneluser>`, `<docroot>` with the live values.

Order, as always: **backup → preflight → migrations (each prints PASS) → code → hard-refresh → sign out/in → verify.**

## 0. Before you start (live, over SSH) — two hygiene checks found on 2026-09-21

    cd /home/<cpaneluser>/<docroot>
    ls -la pw.php application/config/testing 2>&1     # BOTH must say "No such file or directory"
    ls -d install                                      # if it exists: mv install ../install_disabled_$(date +%Y%m%d)

`pw.php` + `application/config/testing/` is the local test harness (an auth bypass when both are present) and
must never be on live. `install/` is the vendor installer; it answered HTTP 200 on live on 2026-09-21 and must
be blocked or moved out of the docroot.

## 4. Deploy the code

Copy the application files from the unpacked zip into the docroot — **not** `db/`:

    cd ~/deploy_e9a34e01
    rsync -av --exclude 'db/' ./ /home/<cpaneluser>/<docroot>/

(or: cPanel File Manager → upload the zip into the docroot → Extract → then delete the extracted `db/`
folder from the docroot; or the cPanel Git route from `DEPLOYMENT.md` once a remote exists.)

**`config.php` note:** the package sets `log_threshold = 1` (error-only logging into
`application/logs/`). Keep it — it is how this bug became diagnosable. Make sure `application/logs/` exists
and is writable (`mkdir -p application/logs && chmod 755 application/logs`), otherwise CI logs nothing.
Do **not** copy `application/config/database.php` — it is not in the package; live keeps its own.

## 5. Hard-refresh, sign out / in

- On every till: **Ctrl+F5** on the POS once (the scripts carry new `?v=` versions, but a tab that is already
  open keeps the old ones until reloaded). On tablets: close the tab and reopen.
- **Sign out and in** on every account that should see the new grants (`pos_26` Manager, `pos_24`/`pos_13`
  everyone): permissions are snapshotted at login.
- Admin → Settings → **Modules**: the Hotel row as before, plus **POS behaviour › Automatic waiter logout
  after order placement = ON** (that is today's behaviour; switch it off only if the network is unreliable).

## 6. The stuck sales — watch them upload, then verify in the database

On each affected waiter device: sign in as that waiter, open the POS, stay on it. Within ~7 s per queued sale the
till shows green **"Sale No … has been uploaded to server"** toasts. A **red persistent toast** ("Sale NOT
uploaded … still queued") means the server still refuses it — send the sale number and the HTTP code it shows.

Then confirm on live (read-only):

    -- orders that were invoiced but are still open in the kitchen table: should be NONE for those waiters
    SELECT sale_no, waiter_id, order_status, sale_date, total_payable
      FROM tbl_kitchen_sales WHERE del_status='Live' AND order_status IN (1,2) ORDER BY id;

    -- what has now been recorded for a waiter since the first affected day
    SELECT sale_no, sale_date, total_payable, paid_amount, order_status, counter_id
      FROM tbl_sales WHERE waiter_id = <waiter user id> AND sale_date >= '<first affected date>' ORDER BY id;

    -- the same figures the Dashboard shows (completed order value for a day / outlet)
    SELECT SUM(total_payable) FROM tbl_sales
     WHERE sale_date = '<date>' AND outlet_id = <outlet> AND order_status = 3 AND del_status = 'Live';

A waiter till is safe to reset only when every invoiced sale from that device is in the second result
(and gone from the first). Sales recorded this way carry the outlet's open-register counter, so they
appear on the register report of that counter.

## 8. If something goes wrong

| Stage | Action |
|---|---|
| A migration printed FAIL | Stop. Nothing else has changed. Send the output. |
| Code deployed, POS misbehaves | Copy back the previous files from the step-1 era docroot backup, or redeploy `3457253b`'s files; the migrations are additive and can stay. |
| Red "Sale NOT uploaded" toasts persist after the deploy | Do NOT reset the till. Send the sale number + HTTP code; the sale is still safe in the device's IndexedDB. Check `application/logs/log-<date>.php` on live for the exception. |
| Anything worse | Restore the step-1 dump. |

Nothing here is destructive: no column or table is dropped or renamed, no existing row is deleted.
